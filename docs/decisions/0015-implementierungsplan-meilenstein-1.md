# 0015 — Schrittweiser Implementierungsplan für Meilenstein 1

**Status:** Umgesetzt — alle 10 Schritte abgeschlossen (2026-11-01). Meilenstein 1 aus Brief Abschnitt 11 ist damit erreicht: Seite erstellen, speichern, öffentlich darstellen, per Docker Compose self-hostbar.

## Kontext

Letzter Punkt aus Brief Abschnitt 12. Ziel laut Brief Abschnitt 11: eine Seite erstellen, speichern, öffentlich darstellen — mit Monorepo, startfähigem Backend, DB-Anbindung, Admin-UI, einfachem Content-Modell, API, einfachem Block-Editor, öffentlicher HTML-Ausgabe, grundlegenden Tests. **Ausdrücklich nicht** Teil von Meilenstein 1: Marketplace, vollständiges Plugin-System, komplexe Theme-Verwaltung, Shop, umfangreiche Benutzerverwaltung — obwohl die Architektur dafür in den ADRs 0005–0013 bereits vorbereitet ist (Gruppen/Capabilities/2FA/Plugin-Isolation/Theme-Editor kommen alle _später_, nicht in diesem Durchgang).

## Entscheidung: die Schritte

Jeder Schritt ist einzeln überprüfbar (Brief-Prinzip 10), baut auf dem vorherigen auf:

1. ~~**Monorepo-Grundgerüst**~~ ✅ — pnpm-Workspace + Turborepo, leere Pakete gemäß [0012](0012-monorepo-struktur.md) (nur `package.json`/`tsconfig`, noch keine Logik), Root-Lint/Format/CI-Skeleton. _Verifikation:_ `pnpm install && pnpm turbo run build` läuft durch (No-Op). **Erledigt:** `pnpm build`, `typecheck`, `lint`, `format:check` und `lint:boundaries` (dependency-cruiser nach [0012](0012-monorepo-struktur.md)) laufen alle grün; Git-Repo initialisiert, noch kein Commit.
2. ~~**Datenbank**~~ ✅ — `packages/database`: Drizzle-Schema für `users`, `content_types`, `content_items` aus [0013](0013-minimales-datenmodell.md) (Rest der Tabellen kann als Schema existieren, bleibt aber ungenutzt), Migrations-Tooling, lokales Postgres via Docker Compose. _Verifikation:_ Migration läuft gegen lokalen Container. **Erledigt:** alle 11 Tabellen aus [0013](0013-minimales-datenmodell.md) als Drizzle-Schema angelegt (`packages/database/src/schema/{auth,content,extensions}.ts`), Migration generiert und gegen lokalen Postgres-Container angewendet (`docker/docker-compose.yml`, Port **5433** statt 5432 — Port 5432 war durch einen anderen, fremden Container auf diesem Rechner belegt; Image **`postgres:15-alpine`** statt 16, weil 16 nicht lokal verfügbar war und der Pull über den konfigurierten Docker-Proxy nicht durchkam — rein pragmatische, folgenlose Abweichung, kein Postgres-16-Feature wird genutzt). `drizzle-kit`/`drizzle-orm` auf die jeweils neueste Version aktualisiert, weil ältere Versionen die NodeNext-`.js`-Imports zwischen den Schema-Dateien nicht auflösen konnten.
3. ~~**`packages/blocks`**~~ ✅ — `BlockDocument`/`BlockNode`-Schema (Zod) aus [0014](0014-api-vertraege.md) + 2–3 Basis-Block-Typen (Absatz, Überschrift, Bild), nur Attribute-Schema, noch kein UI. _Verifikation:_ Unit-Tests validieren Beispiel-Dokumente. **Erledigt:** Zod-Schema, eine `BlockTypeRegistry` zur Typ-Registrierung (Grundlage für spätere Plugin-Block-Typen), die drei Basis-Block-Typen `core/paragraph`, `core/heading`, `core/image`, sowie `validateBlockDocument()` für die serverseitige Prüfung. **Vitest** als Testframework für das ganze Monorepo eingeführt (passt zum Vite-nahen Astro/Admin-Stack); 5 Unit-Tests grün.
4. ~~**`apps/server`-Grundgerüst**~~ ✅ — NestJS mit Fastify-Adapter ([0004](0004-backend-framework.md)), DB-Verbindung, ein Health-Check-Endpunkt. _Verifikation:_ `GET /api/v1/health` antwortet 200 gegen laufende DB. **Erledigt:** `DatabaseModule` stellt die Drizzle-Connection per DI bereit (`DATABASE_CONNECTION`-Token), `HealthController` prüft per `select 1` echte DB-Konnektivität. Manuell gegen den laufenden Postgres-Container verifiziert: `GET /api/v1/health` → `200 {"status":"ok"}`.
5. ~~**Content-API (minimal, noch ohne Auth)**~~ ✅ — ein hartkodierter Content-Typ "page", CRUD + Publish-Endpunkte aus [0014](0014-api-vertraege.md). Auth kommt bewusst erst in Schritt 7 — bis dahin offen und klar als Übergangszustand markiert. _Verifikation:_ Integrationstests legen eine Seite an, lesen, veröffentlichen sie, prüfen DB-Zustand. **Erledigt:** Content-Logik framework-unabhängig in `packages/content` (ADR 0012: kein NestJS dort), `apps/server` verdrahtet nur Controller darüber. `BootstrapService` legt den Content-Typ "page" und einen Platzhalter-`SYSTEM_USER_ID` an (TODO: durch echten eingeloggten User in Schritt 7 ersetzen). Globaler `HttpExceptionFilter` setzt das Fehlerformat aus ADR 0014 (`{error:{code,message}}`) um. Integrationstests gegen die echte DB grün; zusätzlich der komplette Flow per `curl` gegen den laufenden Server verifiziert (Create → Draft unsichtbar öffentlich (404) → Patch → Publish → öffentlich sichtbar (200) → Delete). **Stolperstein behoben:** Turborepo 2.x filtert Umgebungsvariablen standardmäßig (strict env mode) — `DATABASE_URL` musste in `turbo.json` explizit für den `test`-Task deklariert werden, sonst schlugen die Integrationstests nur über `pnpm test` (nicht aber direkt per `pnpm --filter` aufgerufen) mangels DB-Verbindung fehl.
6. ~~**`packages/renderer` + `apps/web`-Grundgerüst**~~ ✅ — Render-Komponente pro Block-Typ aus Schritt 3, Astro-App im On-Demand-Modus ([0014](0014-api-vertraege.md)), dynamische Route ruft die öffentliche Content-API auf. _Verifikation:_ Aufruf einer bekannten Slug-URL im Astro-Dev-Server zeigt die zuvor angelegte Seite als HTML. **Erledigt:** React-Komponenten für die drei Basis-Block-Typen in `packages/renderer` (gemeinsamer Vertrag für Editor-Vorschau und Astro), `apps/web` als Astro-App mit `@astrojs/node`-Adapter (`output: "server"`) und `[...slug].astro`-Route. Live verifiziert: Seite per API angelegt/veröffentlicht, im Astro-Dev-Server unter der Slug-URL korrekt als HTML gerendert (alle drei Block-Typen), unbekannter Slug liefert 404.
7. ~~**Auth (minimal)**~~ ✅ — `packages/auth`: `users`-Tabelle, Passwort-Hashing, Session-Cookie-Login ([0013](0013-minimales-datenmodell.md)). **Kein** Gruppen-/Capability-/2FA-System in diesem Schritt (das ist Vision, nicht Meilenstein 1) — nur: eingeloggt oder nicht, schließt die in Schritt 5 offene Lücke. _Verifikation:_ Redaktions-Endpunkte lehnen unauthentifizierte Requests ab; Login setzt ein gültiges Session-Cookie. **Erledigt:** Passwort-Hashing mit Node-eigenem `scrypt` (keine externe Abhängigkeit), opake Session-Tokens in der `sessions`-Tabelle, `SessionGuard` schützt `ContentItemsController`/`ContentTypesController`. `BootstrapService` legt statt des alten `SYSTEM_USER_ID`-Platzhalters einen echten Admin-Account an (E-Mail/Passwort über `ADMIN_EMAIL`/`ADMIN_PASSWORD`, sonst unsicherer Dev-Default — kein echter Einrichtungsassistent, das bleibt Vision). `content_items.authorId` kommt jetzt aus der Session statt einer Konstante. Live verifiziert: ohne Cookie → 401, falsches Passwort → 401, Login → 200 + Set-Cookie, authentifizierter Request → 200 mit echtem `authorId`, Logout invalidiert die Session serverseitig (altes Cookie danach → 401). **Stolperstein behoben:** `@fastify/cookie` und `@nestjs/platform-fastify` hatten durch pnpm zwei unterschiedliche `fastify`-Versionen im Dependency-Tree (strukturell inkompatible `FastifyInstance`-Typen) — über `pnpm.overrides` in der Root-`package.json` auf eine Version vereinheitlicht.
8. ~~**`apps/admin`-Grundgerüst + einfacher Block-Editor**~~ ✅ — React-App, Login-Screen, Seiten-Liste, minimaler Editor mit den Block-Typen aus Schritt 3 (Reihenfolge ändern reicht zum Start, volles `dnd-kit` kann nachgezogen werden), Autosave (debounced PATCH), "Veröffentlichen"-Button. _Verifikation:_ Manuell im Admin eine Seite anlegen, veröffentlichen, live auf `apps/web` sehen. **Erledigt:** Vite + React (pragmatische Wahl, nicht vorher entschieden), bewusst ohne Router/Tailwind/dnd-kit — drei Views per einfachem State-Switch, Auf/Ab-Buttons zum Umsortieren, minimales handgeschriebenes CSS. API-Typen lokal redeklariert statt über den in ADR 0014 angedachten `/contracts`-Entry-Point (TODO, sobald mehr als eine App diese Typen braucht). Server-seitig: CORS mit konkretem Origin (`ADMIN_ORIGIN`) aktiviert, da Cookie-Auth kein Wildcard-Origin erlaubt. Live im Browser verifiziert: Login → Seite anlegen → Überschrift- und Absatz-Block hinzufügen/befüllen → Autosave ("Gespeichert") → Veröffentlichen → auf `apps/web` unter der Slug-URL mit exakt diesem Inhalt sichtbar. **Stolperstein behoben:** Der API-Client setzte `Content-Type: application/json` auch bei leeren POST-Bodies (publish/unpublish/logout), was der Server mit 400 ablehnte — Header wird jetzt nur bei tatsächlichem Body gesetzt.
9. ~~**Grundlegende automatisierte Tests konsolidieren**~~ ✅ — Unit-Tests (Block-Schema), Integrationstests (Content-API), ein End-to-End-Smoke-Test (Login → Seite anlegen → Block hinzufügen → veröffentlichen → öffentliche URL prüft Inhalt). Erfüllt explizit die Meilenstein-1-Anforderung "Grundlegende automatisierte Tests". **Erledigt:** Unit-Tests (`packages/blocks`, `packages/auth`) und Integrationstests (`packages/content`, `packages/auth`) existierten schon aus den vorherigen Schritten. Neu: ein eigenständiges `e2e/`-Paket (Ergänzung zur Struktur aus [0012](0012-monorepo-struktur.md), nicht Teil der dortigen Abhängigkeitsregeln, da reine Testinfrastruktur) mit einem Smoke-Test, der `apps/server` und `apps/web` (Astro-Preview) selbst als Kindprozesse auf separaten Ports startet und den kompletten Flow per HTTP durchspielt. Läuft grün über `pnpm test`.
10. ~~**Docker Compose fürs Self-Hosting**~~ ✅ — Server + Web + Postgres (Admin kann als statischer Build hinter dem Server mitlaufen) verdrahtet in einem Compose-File. Bewusst letzter Schritt, weil es nur das bereits funktionierende Meilenstein-1-Ergebnis verpackt, keine neue Funktionalität ist. **Erledigt:**
    - `docker/server.Dockerfile` und `docker/web.Dockerfile` — je ein einzelnes Image, das das ganze Repo kopiert und baut (bewusst kein größen-optimierter Multi-Stage-Build mit `pnpm deploy`; Einfachheit vor Image-Größe für Meilenstein 1).
    - `apps/server` liefert `apps/admin`'s Build jetzt unter `/admin` aus (`@fastify/static`, `redirect: true` für `/admin` ohne Slash) und wendet beim Start automatisch ausstehende Migrationen an (`runMigrations()` in `packages/database`) — ein frischer Container braucht keinen manuellen Migrationsschritt.
    - `docker/docker-compose.yml` um die Services `server` und `web` erweitert; `postgres` bleibt unverändert (Port 5433 weiterhin auf den Host gemappt, schadet den Containern nicht, die intern über den Servicenamen `postgres:5432` verbinden).
    - **Root-Skripte angepasst:** `pnpm db:up`/`db:down` beschränken sich jetzt explizit auf den `postgres`-Service (sonst würden sie versehentlich auch `server`/`web` mitstarten und mit lokal laufenden Dev-Prozessen um dieselben Ports konkurrieren). Neu: `pnpm selfhost:up`/`selfhost:down` für den kompletten containerisierten Stack.
    - Live gegen den vollständig containerisierten Stack verifiziert: Health-Check, Login, Seite anlegen/bearbeiten/veröffentlichen, öffentliche Auslieferung über Container-zu-Container-Kommunikation (`web` → `server:3000`), Admin-UI unter `/admin` im Browser.
    - **Zwei Stolpersteine behoben:** (1) `packages/database` baute vor `packages/blocks`, obwohl es davon abhängt (Reihenfolge in den Dockerfiles korrigiert). (2) Vites Standard-`base: "/"` erzeugte absolute Asset-Pfade, die unter `/admin` ins Leere liefen (404) — eigenes Build-Skript `build:selfhosted` mit `--base=/admin/` für den Docker-Build, lokales `pnpm dev`/`build` bleibt unverändert auf `/`.

## Explizit ausgeklammert (gehört zur Vision, nicht zu diesem Durchgang)

Marketplace, volles Plugin-System mit Prozess-Isolation, Theme-Online-Editor, Gruppen/Capabilities/2FA, Content-Revisions-Browsing-UI, Custom-Content-Typen jenseits von "Page", Update-Check-Dashboard. Die Architektur (ADRs 0005–0013) ist dafür vorbereitet, die Umsetzung kommt nach Meilenstein 1 in eigenen, separat freizugebenden Schritten.

## Konsequenzen

- Dies ist der "erste konkrete Implementierungsschritt" im Sinne von Brief Abschnitt 12 — die eigentliche Umsetzung (Schritt 1 ff.) beginnt erst nach expliziter Freigabe, nicht automatisch mit dieser Dokumentation.
- Damit sind alle fünf Punkte aus Brief Abschnitt 12 bearbeitet.
